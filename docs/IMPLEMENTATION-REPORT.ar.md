## 2. منهجية العمل: لماذا التشغيل الفعلي وليس المراجعة النظرية فقط؟

بيئة العمل (sandbox) هي بيئة Linux لا تحتوي على .NET SDK ولا على Windows، لذلك لا يمكن تجميع أو تشغيل مشروع WinUI 3 محليًا. ولتفادي الوقوع فيما حذّر منه الطلب الأصلي — وهو الاعتماد على فحص نصي سطحي (مثل عدّ الأقواس بلغة Python) وادّعاء أن الكود "سليم" دون تجميعه فعليًا — تم اعتماد الإستراتيجية التالية:

1. مراجعة الكود يدويًا أولًا لاكتشاف الأخطاء الواضحة (أخطاء منطقية، حزم ناقصة، أخطاء Cast).
2. دفع كل إصلاح إلى GitHub ثم تشغيل workflow حقيقي (`.github/workflows/ci.yml`) على خادم `windows-latest` بصلاحيات .NET 8 SDK حقيقية.
3. قراءة رسالة الخطأ **الفعلية الدقيقة** الصادرة عن المُصرِّف (compiler) أو عن منفّذ الاختبارات (test runner) من واجهة GitHub Checks API.
4. إصلاح ذلك الخطأ تحديدًا، ثم تكرار العملية — 14 مرة متتالية — حتى اختفت كل الأخطاء.

بهذا الأسلوب، كل سطر في هذا التقرير مبني على دليل حقيقي (رقم تشغيل CI + نص الخطأ الفعلي)، وليس على افتراض.

### الجولة 13–14: إصلاح السببين الجذريين الحقيقيين الأخيرين لفشل الاختبارات

**السبب الجذري الأول — عدم تطابق مفتاح توقيع JWT (Run `44840554704` → إصلاح بـ `8a3375b`):**

ملف `Program.cs` يقرأ `Jwt:SigningKey` و `ConnectionStrings:Postgres` إلى متغيرات محلية **قبل** تنفيذ `WebApplicationBuilder.Build()`. وبما أن `WebApplicationFactory` (في الاختبارات) يدمج إعداداته التجريبية (`ConfigureAppConfiguration`) فقط أثناء تنفيذ `Build()` نفسه، فإن تلك القراءة المبكرة لا ترى الإعدادات التجريبية إطلاقًا. والنتيجة: خدمة `TokenService` وقّعت رموز JWT بمفتاح الاختبار الصحيح، بينما إعداد `AddJwtBearer` (الذي يتحقق من التوقيع) ظلّ يحمل المفتاح الوهمي الافتراضي من `appsettings.json` — فكانت **كل** نقاط النهاية المحمية بـ `[Authorize]` ترجع `401 Unauthorized` دائمًا، بغض النظر عن صحة الرمز المُرسل.

الإصلاح: في `BecettiApiFactory.cs`، تم ضبط هذه القيم كمتغيرات بيئة نظام (environment variables) بصيغة الشرطة السفلية المزدوجة (`Jwt__SigningKey` إلخ)، لأن هذه المتغيرات تُقرأ بواسطة `WebApplication.CreateBuilder(args)` نفسها قبل أي سطر من كود `Program.cs` الخاص بالتطبيق — أي أنها تصل في الوقت المناسب فعلًا.

بعد هذا الإصلاح (Run `44840554704`)، اختفى خطأ 401 تمامًا، لكن ظهر خلفه خطأ حقيقي جديد:

**السبب الجذري الثاني — عدم قدرة SQLite على الترتيب حسب أعمدة DateTimeOffset (إصلاح بـ `5d98895`):**

اختبار `Updates_NoReleases_ReturnsNoUpdate` فشل بخطأ `500 Internal Server Error`، وتتبّع الاستدعاء (stack trace) أظهر أن الخطأ ينشأ من السطر 35 في `UpdatesController.cs`، تحديدًا من استعلام `OrderByDescending(r => r.PublishedAt)`. السبب: قاعدة بيانات SQLite (المستخدمة فقط في بيئة الاختبار) لا تدعم ترتيب الاستعلامات حسب نوع `DateTimeOffset`، وترمي استثناء `NotSupportedException: SQLite cannot order by expressions of type 'DateTimeOffset'`. هذا قيد معروف وموثّق في مزوّد SQLite لـ Entity Framework Core، ولا علاقة له إطلاقًا بقاعدة بيانات الإنتاج الحقيقية (PostgreSQL).

الإصلاح: في `AppDbContext.cs`، تم تطبيق `DateTimeOffsetToBinaryConverter` تلقائيًا على كل خاصية من نوع `DateTimeOffset`/`DateTimeOffset?` في جميع الكيانات (entities)، **فقط** عندما يكون مزوّد قاعدة البيانات النشط هو SQLite — أي أن مسار PostgreSQL للإنتاج لم يُمسّ إطلاقًا.

**النتيجة النهائية (Run `44840966151`):** بناء ✅ ناجح، اختبارات ✅ ناجحة بالكامل، صفر أخطاء، صفر تحذيرات أو ملاحظات من أي نوع (تم التأكد عبر GitHub Checks API — مصفوفة فارغة تمامًا من أي annotation فشل).

### الجولة 15: تحقق حقيقي من الاتصال بقاعدة بيانات PostgreSQL (Run `44841506040`)

بعد وصول CI إلى حالة خضراء تمامًا، تمت إضافة مهمة (job) جديدة باسم `postgres-migrations` إلى `ci.yml` تعمل على خادم `ubuntu-latest` (نظرًا لأن خوادم Windows المستضافة من GitHub لا تدعم حاويات الخدمات/service containers)، وتقوم بما يلي فعليًا لا نظريًا:

1. تشغيل حاوية **PostgreSQL 16 حقيقية** كخدمة مصاحبة للمهمة.
2. تثبيت أداة `dotnet-ef` الرسمية.
3. تنفيذ `dotnet ef database update` ضد تلك القاعدة الحقيقية لتطبيق الهجرة (migration) الموجودة في المشروع (`20261120000000_InitialCreate`).
4. التحقق عبر `psql` من أن الجداول الخمسة المتوقعة (`Users`, `RefreshTokens`, `ReputationEntries`, `ReleaseVersions`, `AuditLogs`) أُنشئت فعلًا داخل قاعدة البيانات.

وقد تطلّب هذا أيضًا إضافة حزمة `Microsoft.EntityFrameworkCore.Design` المفقودة إلى `Becetti.Security.Api.csproj`، التي بدونها كانت أداة `dotnet-ef` سترفض العمل مع المشروع من الأساس.

**النتيجة:** ✅ نجاح كامل — هذه أول مرة تُختبر فيها هجرات قاعدة البيانات ضد PostgreSQL حقيقي بدلًا من SQLite فقط، وأثبتت أن مخطط قاعدة البيانات (schema) يُطبَّق بنجاح على محرك الإنتاج الفعلي.

## 3.5 حزمة MSIX موقّعة جاهزة للتحميل (تحديث لاحق)

بعد طلب المستخدم رابط تحميل، تمت إضافة مهمة جديدة لـ CI باسم `package-msix` تقوم بما يلي فعليًا على خادم `windows-latest`:

1. توليد شهادة توقيع ذاتية التوقيع (self-signed) حقيقية بامتداد Code Signing الصحيح.
2. بناء وتعبئة حزمة **MSIX حقيقية وموقّعة فعليًا** باستخدام الطريقة الرسمية الموثّقة من Microsoft لمشاريع WinUI 3 أحادية المشروع (`msbuild` + `UapAppxPackageBuildMode=SideloadOnly` + `GenerateAppxPackageOnBuild=true`).
3. **التحقق داخل CI نفسه** من أن الحزمة الناتجة تحتوي فعليًا على ملف `AppxSignature.p7x` (دليل أنها موقّعة فعلًا وليست مجرد معبّأة) وملف `AppxManifest.xml` صالح — عبر فتح ملف MSIX كأرشيف zip والتأكد من وجود هذين العنصرين، وهذا نجح فعليًا (Run [`44844789535`](https://github.com/Ahmedbecett/BECETTI-SECURITY/actions/runs/44844789535)).
4. نشر الحزمة الموقّعة + الشهادة العامة (`.cer`) + تعليمات تثبيت (`INSTALL.txt`) كأصول (assets) ضمن إصدار (Release) علني على GitHub.

https://github.com/Ahmedbecett/BECETTI-SECURITY/releases/tag/msix-test-1b738db

⚠️ **تنبيه مهم**: هذه حزمة اختبار (sideload) موقّعة بشهادة ذاتية التوقيع، **وليست** موقّعة من جهة إصدار شهادات موثوقة (CA) ولا من هوية ناشر Microsoft Partner Center حقيقية. لذلك يجب تثبيت الشهادة العامة (`BecettiTestCert.cer`) يدويًا والوثوق بها قبل أن يقبل نظام Windows تثبيت الحزمة — الخطوات الدقيقة موجودة في ملف `INSTALL.txt` المرفق داخل الإصدار نفسه. تقديم المنتج الحقيقي على متجر Microsoft Store يتطلب هوية ناشر حقيقية من Partner Center، كما هو موضّح في `docs/STORE-SUBMISSION.md`.
